# MoveMentor · 动译师

**把年轻人的健身动作，实时翻译成老人、膝痛人群和轮椅使用者能做的低冲击版本。**

核心是一台用 **MoonBit** 从零写成的「动作安全翻译引擎」：一张用领域语言（DSL）描述的规则表 + 一个约束校验器 + 一个抗抖动计数状态机。浏览器只负责两件事——拿到人体关键点、把结果读出来。翻译逻辑一行 JavaScript 都没有。

> 本工具输出的是**降低关节负荷的运动变式**，不构成医疗建议、诊断或康复处方。使用前请咨询医生或康复治疗师。完整边界见 [`docs/06-安全边界与免责声明.md`](docs/06-安全边界与免责声明.md)。

---

## 1. 它解决什么问题

一个五六十岁的膝痛人群，或者一位轮椅使用者，看到「跟练开合跳」这类视频时，实际处境是**没有可执行的下一步**：

- 照做 → 有受伤风险；
- 不做 → 完全放弃运动；
- 自己改 → 不知道改哪里、改成什么程度。

现有的健身内容几乎都是「按标准动作演示 + 让你尽量做到位」，而「做不到位怎么办」这一段是空的。

MoveMentor 填的就是这一段：**把「这个动作你做不了」翻译成「这个动作你可以这样做」**，并且给出可数、可练、有指导语的版本。

## 2. 三十秒看懂它做了什么

```
源动作：开合跳（跳跃 · 高冲击 · 双侧）
目标人群：膝痛 / 老年低冲击人群（膝关节活动上限 105°、不允许跳跃与落地）

↓  翻译引擎

目标动作：坐姿抬腿（单腿）（坐姿 · 无冲击 · 膝关节负荷 low）
理由：去掉跳跃与落地冲击，把下肢工作改成坐姿抬腿，保留髋与膝的主动活动
指导语：「坐稳在椅子上，双脚平放地面，背部离开椅背。」
        「缓慢抬起右小腿，抬到膝盖接近水平，停一下再慢慢放下。」
```

这段过程不是调用大模型猜的，而是**查表 + 校验**算出来的，因此可复现、可审计、可测试。

## 3. 快速开始

### 3.1 跑测试（不需要摄像头、不需要网络）

```bash
moon test --target js
# Total tests: 69, passed: 69, failed: 0.
```

### 3.2 跑引擎自检（推荐的验收入口）

```bash
moon run cmd/main --target js
```

它会依次打印：

1. 规则表统计与解析诊断；
2. **每一条翻译规则的约束校验结果**（逐条打勾，证明「翻译出来的动作没有被目标人群的能力上限违反」）；
3. 基线人群（一般成年人）的**恒等映射**验证；
4. 离线演示：每条规则用合成姿态跑 12 秒，打印完成次数与指导语；
5. 反向翻译：从受限动作能否回溯到源动作。

其它子命令：

```bash
moon run cmd/main --target js -- dsl                        # 打印内置规则表 DSL 原文
moon run cmd/main --target js -- metrics                    # 打印各动作的指标扫描（调阈值时看这张表）
moon run cmd/main --target js -- translate jumping_jack elderly_knee_pain
moon run cmd/main --target js -- demo squat wheelchair 10   # 跑 10 秒
```

### 3.3 打开演示页面

页面通过 ES module 直接引用构建产物，所以需要用一个本地 HTTP 服务打开（不能用 `file://`）：

```bash
moon build --release --target js   # 注意 --release：页面引用的是 release 产物
python -m http.server 8000         # 在仓库根目录执行
# 浏览器打开 http://localhost:8000/web/
```

页面有两种模式：

- **合成姿态模式（默认，离线可用）**：由引擎按当前动作的 DSL 阈值生成一段确定性的假骨架，用来验证「翻译 → 计数 → 指导语」整条链路。不需要摄像头，也不需要联网，断网也能演示。
- **摄像头模式**：从 CDN 加载 MediaPipe Pose，把 33 个关键点拍平成 132 个数交给引擎。首次使用需要联网下载模型。

### 3.4 一段演示就是一个 URL

页面支持用查询参数直达任意演示状态，**截图、录屏和评审复现都不依赖手动点击**：

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| `motion` | 动作 id | 源动作，如 `jumping_jack` / `squat` / `plank` |
| `audience` | 人群 id | 如 `elderly_knee_pain` / `wheelchair` / `office_sedentary` |
| `source` | `synthetic` \| `camera` | 姿态来源，默认合成 |
| `auto` | `1` | 打开后自动开始 |
| `warm` | 秒数 | **先把这么多秒的合成姿态一次性喂给引擎**，让计数器直接落在某个进度上 |
| `speak` | `0` \| `1` | 语音播报开关 |

例如复现「开合跳 → 膝痛版坐姿抬腿，已经做了 5 次」：

```
http://localhost:8000/web/?motion=jumping_jack&audience=elderly_knee_pain&auto=1&warm=9&speak=0
```

`warm` 走的是和命令行自检、单元测试完全相同的那条链路（`api_synth_landmarks` → `api_step_json`），所以页面上显示的数字和 `moon run cmd/main` 打印的是同一套结果。

## 5. 架构：三层，边界只有 132 个数

```
┌─────────────────────────────────────────────────────────────┐
│  演示层   web/（浏览器）      cmd/main（命令行）            │
│  职责：取姿态、画骨架、放语音、打印结果                     │
│  可以随时换掉，不影响任何翻译逻辑                           │
└───────────────────────────┬─────────────────────────────────┘
                            │  进来：132 个 Double（33×x/y/z/visibility）
                            │  出去：一个 JSON 字符串
┌───────────────────────────▼─────────────────────────────────┐
│  桥接层   src/bridge/        唯一接触浏览器的包             │
│  职责：会话状态、ESM 导出、把 FFI 包成页面能调的函数        │
└───────────────────────────┬─────────────────────────────────┘
                            │  纯函数 + 纯数据结构调用
┌───────────────────────────▼─────────────────────────────────┐
│  核心引擎 src/engine/        全 MoonBit，不依赖任何宿主     │
│  DSL 解析 → 约束校验 → 翻译求解 → 计数状态机 → 指导语       │
│  全部可在没有浏览器、没有摄像头、没有网络的环境下测试       │
└─────────────────────────────────────────────────────────────┘
```

**这条边界为什么重要**：视频、图像和模型推理全部留在浏览器侧，引擎永远看不到画面，只拿到一串坐标数字。这既让引擎可被完整测试，也让隐私边界是结构性的而不是承诺性的（见 §9）。

换掉 MediaPipe（比如换成别的姿态模型）只需要改 `web/app.js` 里拍平数组的那几行；换掉前端框架不影响引擎；把引擎搬到服务端也不需要改引擎代码。

## 6. 规则表 DSL

规则表不是硬编码的结构体，而是一段可读的文本。它读起来就是一张「动作 → 人群 → 变式」的表格，医生和评审都能直接审。

```
motion squat
name 徒手深蹲
view front
tag strength
load knee=high                      # 对膝关节的负荷等级：high
phase down hold=200 hip_height_ratio<=0.760    # 蹲下：髋高比降到 0.76 以下
phase up hold=200 hip_height_ratio>=0.790      # 站起：髋高比升回 0.79 以上
cycle down up                       # down → up 算一次
min_rep_ms 700                      # 两次计数至少间隔 700ms
hysteresis 0.010                    # 相位迟滞带宽，抗边界抖动
cue 髋部向后向下坐，膝盖尽量不超过脚尖

audience elderly_knee_pain
name 膝痛 / 老年低冲击人群
limit knee_left<=105                # 能力上限：膝关节活动不超过 105°
limit trunk_lean<=15
allow impact=none                   # 只能接受无冲击动作
allow knee=low                      # 膝关节负荷只能到 low

variant squat elderly_knee_pain -> chair_squat
reason 保留蹲起模式，限制下蹲幅度并提供椅背支撑，把膝负荷降到低位
```

### 6.1 关键设计：约束校验只有一种类型

`Constraint` 这个类型同时被两处使用：

- 动作侧：`load knee=high` 表示「做这个动作，膝关节要承受 high 负荷」；
- 人群侧：`allow knee=low` 表示「这个人群的膝关节最多承受 low 负荷」。

于是校验退化成一次**等级比较**：`动作要求 3 > 人群允许 1` → 冲突。同一套比较逻辑既用于 `limit metric<=value`（角度类上限）也用于 `allow axis=level`（负荷轴上限）。

好处是**「翻译不出来」是一个显式结果，而不是一个猜测**：

| 结果 | 含义 |
| --- | --- |
| `Translated` | 规则表里有这个（动作，人群）专属变式 |
| `Substituted` | 没有专属变式，但存在标签相近的替代动作 |
| `Unsupported` | 明确拒绝给出方案，并说明原因——**绝不猜** |

`Unsupported` 是这个项目里最有价值的分支：在健康场景下，「我不知道」比「看起来差不多」安全得多。

### 6.2 指标注册表

所有约束都只通过**指标名**耦合，接一个新自由度 = 在 `metrics.mbt` 加一个分支，其余代码不动。

选指标的取舍是「正面机位下稳不稳」：

| 指标 | 含义 | 备注 |
| --- | --- | --- |
| `knee_left` / `knee_right` | 膝夹角（髋–膝–踝） | 正面下看对称性；深度信息弱 |
| `hip_left` / `hip_right` | 髋夹角 | |
| `shoulder_left/right`、`elbow_left/right` | 肩外展、肘夹角 | |
| `trunk_lean` | 躯干相对竖直的倾角 | |
| `ankle_span` | 双脚开度（肩宽倍数） | 归一化，抵消身高与机位远近 |
| `knee_lift_left/right` | 抬膝程度（髋–踝竖直距倍数） | |
| `shin_drop_left/right` | 小腿下垂（躯干长倍数） | 坐姿抬腿最稳的读数 |
| `wrist_above_shoulder_left/right` | 手腕高出肩的程度（躯干长倍数） | 举臂类动作 |
| `hip_height_ratio` | 髋高比（站/坐/蹲程度） | **正面机位判断深蹲最稳的量** |
| `confidence` | 关键点平均可见度 | 低于阈值直接丢弃该帧 |

正前方看不到屈膝深度，所以深蹲类动作不用 `knee_*` 而用 `hip_height_ratio`。这是被摄像头机位约束逼出来的设计，写在这里以免后人误改。

## 7. 计数状态机：三条抗抖动防线

「数错次数」是最容易毁掉体验的 bug——用户做了 9 个，界面说 17 个。计数器用了三道防线：

1. **相位迟滞**：进入 `down` 需要 `hip_height_ratio <= 0.760`，退回 `up` 需要 `>= 0.790`，中间 0.03 的带宽内保持当前相位不变，避免在阈值上反复横跳。
2. **最小重复间隔 `min_rep_ms`**：两次计数之间的最小时间，过滤掉高频噪声造成的假计数。
3. **dt 钳制**：单帧时间差上限 `MAX_DELTA_MS = 200`，防止标签页切回来时一个巨大的 dt 把状态机冲飞。

外加一条：**低置信帧直接丢弃**（`confidence < MIN_CONFIDENCE = 0.5`），返回 `LowConfidence` 事件而不是硬猜。

这三种防御各自都能被测试单独触发（见 `counter_wbtest.mbt`），不是「感觉上加了」。

## 8. 翻译完整性的保证怎么证明

一句「我们的引擎是对的」没有意义，所以做了三层可执行的证明：

1. **单元测试 69 条**：DSL 解析（含坏输入的诊断行号）、几何、指标、翻译求解、计数状态机、JSON 输出、合成姿态。
2. **规则表回归测试**：`内置规则表回归：每一条映射都必须通过约束校验` —— 只要有人往规则表里加了一条「膝痛人群去做深蹲到底」这样的坏映射，测试立刻红。
3. **自检工具**：`moon run cmd/main` 对全部 9 条映射逐条打印校验结果，并验证基线人群是恒等映射、每个受限人群都能拿到方案。

这三者跑出来的结果都是确定性的，重复运行完全一致，可以直接作为参赛验收证据。

## 9. 隐私边界（结构性，不是承诺性的）

- **画面不出设备**：视频帧、图像和模型推理全部在浏览器侧完成，进引擎的只有 132 个浮点数。
- **没有网络请求**：合成姿态模式下完全离线；摄像头模式只在首次加载 MediaPipe 模型时需要联网。
- **没有账号、没有存储、没有上报**：引擎不写文件、不连数据库、不发请求。
- **不录制**：页面不保存任何视频帧。

这意味着「我们不上传你的画面」不是一句需要相信的承诺——**引擎在架构上根本收不到画面**。

## 11. 已知边界

诚实地写出来，比被评审问出来好：

- **规则表规模小**：9 个动作 / 4 类人群 / 9 条规则，是「可运行的完整闭环」而不是「覆盖全民的数据库」。
- **姿态估计有物理误差**：MediaPipe 在遮挡、宽松衣物、侧面机位下会漂移；当前指标都选了正面机位下最稳的量，但没有做多帧平滑之外的滤波。
- **没有临床验证**：所有阈值来自动作生物力学的常识性取舍（比如膝关节活动上限 105°），**没有做过任何临床实验**，因此措辞上只说「降低关节负荷」，不说「安全」或「有效」。
- **单侧动作需要用户自己换边**：坐姿抬腿目前只跟踪右腿，指导语里提示「做完一组换左腿」，引擎还没做自动换边。
- **没有佩戴设备接入**：心率、血氧等信号没有接入，所以无法根据实时生理状态调整强度。
